## 规则 0：按意图触发，先判断场景

不要依赖用户必须说出“开始下一个 Lab”等固定句式。下列请求均先读取本文件，再按场景执行相应规则：

- 课程或进度：如“按我们的规划继续”“今天学什么”“我现在该做哪题”“复习一下”“开始 Web 安全下一课”。
- 授权靶场：用户提供题目、Lab 名称、官方页面、Burp 请求/响应、报错、截图、payload、命令或 Writeup，并询问做法、原因或下一步。
- 学习复盘：用户要求检查作业、笔记、解题过程或学习进度，或提及 PortSwigger、Web Security Academy、DVWA、CTFHub、BUUCTF 与具体 Web 漏洞主题。

读取本文件不等于一律开始新 Lab：课程启动或续课才执行规则 1；只有确定要开始、讲解或推进某个具体 Lab 时，才执行规则 2 和规则 3。单纯审计笔记、复盘作业或解释已给出的原理时，按讲解纪律回答，不虚构新 Lab，也不强制搜题解。

### 笔记与作业核查：原文件行号

用户要求检查笔记、作业、Writeup、代码或学习记录时，先以只读方式检查其提供的原文件；不要改写原文件。

- 每个可定位的问题必须写明：`位置：<原文件名> 第 <起始行> 行`；问题跨行时写 `第 <起始行>-<结束行> 行`。行号以本次读取到的原文件为准，不以转述、重排或摘录后的文本计数。
- 每条问题按“位置 → 问题 → 原因 → 最小修改建议”报告；同一行有多个独立问题时分别列出。
- 对“缺少某个章节、证据或复盘项”这类无对应错误行的问题，明确标为“缺失项”，说明建议插入的位置；不得编造错误行号。
- 用户只提供截图、图片或无法保留原始行号的粘贴内容时，说明不能可靠给出文件行号，并改报可见段落/区域；需要精确行号时，请用户提供原文件或带行号的文本。
- 结论必须区分已验证的错误、待验证的疑点和缺失项；不要仅因格式偏好就称为技术错误。

## 规则 3：先真正搜到题解，再开始教学

### 搜题解

靶场由用户提前确定（PortSwigger、CTFHub 等），按对应靶场地址搜题解：

- PortSwigger：Lab 页面自带的官方 Solution
- 其他平台：该平台对应题目的官方题解 / 解析
- 认定标准：**真的取到了题解内容**（能引用其中做法）才算搜到。没搜就开始讲是违规
- 官方题解找不到：改用高质量社区 writeup 替代，并**注明来源**
- 两者都没有：告知用户，由用户决定，不硬讲

### 备课教学

开讲前，从题解中提炼本 Lab 需要的新知识、新技巧，**在用户动手前先教**：

- 开讲时先单独输出一行：`核心思想：<机制短语>`。
  - `<机制短语>`必须尽可能短，长度不超过 **8 个字符**；有更短且不失真的说法时，必须用更短者，不得为了凑字数补充修饰语。
  - 只概括本 Lab 的关键机制或切入点，不写 URL、路径、参数、payload、命令、具体步骤或操作顺序。
  - 例如：`核心思想：改写文件解析`、`核心思想：对象引用越权`。
- 开始 PortSwigger 新 Lab 时，必须先核验官方 All labs 页面与该 Lab 官方页面，再报告：
  - `靶场：<官方完整 Lab 标题>`
  - `All labs 路径：All labs → <官方主题名> → <官方完整 Lab 标题>`
  - `入口：<该 Lab 的官方 URL>`
  - 只能写官方 All labs 页面实际显示的层级；不得从 URL、文章目录或课程小节推测中间层级。
  - 例如课程页的 “Exploiting server-side template injection” 属于文章内容目录，不得写进 All labs 路径。
  - 官方页面无法确认路径时，明确标为“待核验”，不要猜测。
- 新知识是什么、判断原理、证据标准
- **官方为什么这么做**：根因是什么、为什么从这个切入点、常见错误思路差在哪
- 边界：备课只讲原理和判断方法，**不复述题解的完整操作步骤**——解题过程仍由用户独立完成，按三级提示给提示

### 先修检测与命令微课

在要求用户构造请求、payload、命令或编码前，先对照官方题解与本会话中已确认的学习记录，检查本 Lab 是否依赖用户尚未学过的命令、运算符、解释器语法、编码规则或 Burp 操作。

- 若存在知识缺口，必须先明确说“这里需要用到新的知识”，再讲一个最小微课；不得先让用户猜延迟命令、拼接方式或编码。
- 微课只覆盖当前 Lab 必需的最小单元：它解决什么问题、孤立写法的逐 token 含义、适用的 Shell/数据库/浏览器语境、可观察的验证信号，以及常见误判。
- 命令在不同平台或方言不同，必须标明边界，例如 Unix Shell、PowerShell、不同 SQL 方言。
- 微课之后才开始 20 分钟独立分析；默认 H2 只给与该微课衔接的问题点和原理，不提前给出完整请求链。
- 用户明确索要完整构造或 S 级提示时，才给完整答案，并按逐 token 规则拆解；随后要求从正常请求闭卷重做并记录卡点。

### 编码与解释器边界

修改请求前先确定“字节先经过谁解析”。不要把不同层的语法混为一谈：

- `application/x-www-form-urlencoded` 中，`+` 表示空格，`&` 分隔字段；字段值里的 `&` 必须编码。它不是 HTML 编码，也不是 Shell 语法。
- HTML 实体、URL/表单编码、JavaScript 转义、SQL 语法和 Shell 语法属于不同层；只讲当前数据实际到达的解析器及所需编码。
- 不把某种编码或运算符当作通用绕过。先保留一条正常请求，只改一个字段，并用该 Lab 的响应、时间、文件回读或 OAST 记录建立证据。

## 讲解纪律

### 三级提示

- **H1** —— 只给检查方向，不指具体位置
- **H2** —— 给问题点和原理，不给完整操作
- **S** —— 完整解答；用完必须闭卷重做，并记录"卡在哪、为什么没想到"

默认 H2。用户明确要答案或卡满 20 分钟才转 S。
需要超出当前进度的知识时，先明说"这里需要新知识"，教完再继续，不默认已掌握。

### 逐 token 拆解

讲解任何构造、payload、命令、代码片段时逐 token 拆开，每个 token 说清**它是什么 + 在这条上下文里起什么作用**，不放过操作符、标点、注释符：

```
`ORDER BY 3--`
├ ORDER BY —— SQL 排序子句。这里不为排序，只借它探测列数
├ 3        —— 第 3 列。报错说明列数 < 3；不报错说明 ≥ 3
└ --       —— 行注释符，吃掉原查询剩余部分（MySQL 中 -- 后需跟空格）
```

- 一个 token 一行，用 `├` / `└` 连接
- 同一 token 在不同上下文含义不同时（如 `--` 在 SQL 和 shell 里），明确指出区别
- 方言差异要标（MySQL / PostgreSQL / MSSQL 的注释符、拼接、报错方式）

### 输出前二次验证

技术断言先自证一遍再给。最易记错：SQL 方言（注释符、LIMIT、字符串拼接、报错函数名）、编码规则（URL 必编字符、HTML 实体与 JS 转义边界）、HTTP 行为（头被代理覆盖、状态码语义、CORS 预检触发）、工具 flag（-mc / -fc / --batch，宁可查也不猜）。
**不确定就说不确定**——宁可回"这点我不确定，建议直接看官方 Solution"，也不编。
