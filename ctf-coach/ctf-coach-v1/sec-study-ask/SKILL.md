# 安全学习提问助手

## 这个 skill 解决什么

提问被打断，通常不是因为模型"不信你是学生"，而是因为**单条消息的内容特征**落在高风险模式里：

| 高风险特征 | 例子 |
|---|---|
| 索取成品 | 直接要 payload、脚本、完整利用链 |
| 指向真实目标 | 出现真实域名 / IP / 具体站点 |
| 可执行的攻击细节 | 绕过某个具体 WAF 的编码技巧、免杀、拿凭据的完整链 |
| 零上下文 | 上来就是"命令注入怎么打" |

开场声明"我仅用于学习"作用有限：它**不在被判定那条消息里**，多轮之后早已衰减出上下文。

真正有效的三件事：

1. **补全真实上下文**（具体靶场、Lab 名、当前进度）—— 不编造
2. **抬高抽象层级**：问"为什么 / 怎么判断 / 如何验证"，而不是"给我什么"
3. **先给出自己的分析再让它挑错**，而不是让它产出

## 硬性边界（不可越过）

这个 skill 只做**诚实改写**，不做伪装：

- 不伪造身份、学校、课程、授权、机构
- 不写"让过滤器以为……"的话术
- 不把请求的真实目的藏起来或换个说法掩盖
- 不把"我要一个可用载荷"包装成"我要原理"

如果用户真正想要的是**针对未授权目标的可用攻击成品**，直接说明这一点，不要用改写来绕过。这种情况改写也帮不上忙 —— 被判定的就是那条消息本身。

改写只改变**提问的抽象层级和上下文完整度**，不改变事实，也不改变你到底想要什么。

## 工作流程

### 第 1 步：风险画像

读用户原始问题，标出命中了哪些高风险特征（对照上面的表）。如果一条都没命中，说明它本来就安全，直接正常回答即可，不必走这个流程。

### 第 2 步：确认事实

从用户处或已有材料里取真实信息，缺什么问什么，**不要替他编**：

- 靶场 / 环境：PortSwigger Academy？DVWA？CTFHub？BUUCTF？本地？
- 如果是 PortSwigger Lab，要**完整的英文 Lab 名**（页面标题）
- 当前进度：本周在学哪一类漏洞
- 卡在哪一步：已经试过什么、观察到了什么

### 第 3 步：改写

三条规则：

1. **加真实上下文** —— 用 `references/context-card.md` 的模板
2. **换问法** —— 把"给我 X"改成"我怀疑 Y，怎么验证 Y"；`references/rephrase-table.md` 有六类漏洞的对照
3. **标注提示等级** —— 按用户自己的 H1 / H2 / S 三级制度标注这次想要哪一级：

   - **H1**：只给检查方向，不指具体位置
   - **H2**：给问题点和原理，不给完整操作
   - **S**：完整解答（用完必须闭卷重做）

   标注等级本身就能明显降低触发概率，因为它等于明确说了"我不要成品"。

### 第 4 步：输出

按下面对话框格式输出，三段，不要长篇解释。

## 输出格式

```
【上下文卡】（新开对话时先贴这段）
背景：……
环境：……
当前进度：……
涉及 Lab：……
我需要：……
我不需要：……

【改写后的问题】（提示等级：H1 / H2 / S）
……（一条可以直接复制粘贴的问题）

【为什么这么改】
- 原问题命中了：（哪几个高风险特征）
- 改动的点：（补了什么上下文 / 抽象层级从哪抬到哪）
- 如果这条还是被拒：改问防御侧或检测侧（例如"这个漏洞在生产环境怎么被检测出来"），
  或直接查该 Lab 的官方 Solution / 官方文档
```

## 判断标准

改写后的问题应当满足：

- [ ] 上下文里没有任何编造内容
- [ ] 问的是"为什么 / 怎么判断 / 如何验证 / 怎么修"，不是"给我一条能用的"
- [ ] 有明确的 Lab 名或环境名
- [ ] 如果真的被拒，用户知道替代路径（官方 Solution、文档、CTF 社区）
